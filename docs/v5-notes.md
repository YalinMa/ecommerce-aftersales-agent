# V5 学习笔记：评测与可观测

> 路线图里 V4 是 MCP 化。评测是迭代速度的瓶颈，所以先做了 V5。

## 为什么需要自动评测

到 V3 为止，每次改动后的验证方式是"回放 + 自动检查 + 人工逐条看对话"：

| 方式 | 能判断什么 | 问题 |
|---|---|---|
| 自动检查（`checks`） | 调没调对工具、转没转人工、有没有写库 | 判断不了回答对不对 |
| 关键词检查 | "已提交"等说法 | 不懂否定和条件：把"提交成功我再告诉您"当成违规 |
| 人工复核 | 一切 | 3 个模型 × 14 个场景 = 42 段对话，每次改动都要看一遍 |

V5 加了**模型评分**（LLM-as-a-judge）：用一个更强的模型充当质检员，逐条判断对话是否满足期望，并给出理由。

## 评分怎么设计

```
评分模型的输入：
  ├─ 知识库全文              ← 政策的唯一依据，评分模型自己的"常识"不算数
  ├─ 场景的期望清单          ← 逐条判断
  └─ 对话记录
       ├─ 用户说的话、客服的回复
       ├─ 每次工具调用和返回的完整数据   ← 业务事实
       └─ [程序记录]：本轮是否真的转了人工、是否真的提交了申请

评分模型的输出（JSON）：
  ├─ 每条期望：通过 / 不通过 + 理由
  ├─ 三个维度 1–5 分：准确性、合规安全、服务体验
  └─ 发现的问题清单

是否通过 = 所有期望都满足 且 准确性 ≥ 4 且 合规 ≥ 4      ← 由代码计算，不让评分模型直接决定
```

几个关键选择：

- **评分依据只给事实。** 工具返回的数据是业务事实，知识库是政策依据。客服说出知识库里没有的规则，就判为编造。
- **每个分数都有锚点描述。** 比如准确性"1 分 = 编造了政策、数据或出处"，避免评分模型凭感觉给分。
- **通过与否由代码算。** 评分模型只负责逐项判断，最终结论按固定规则计算，保证不同评分模型、不同时间的标准一致。
- **评分模型用更强的 `deepseek-v4-pro`。** 被评的客服用的是 `deepseek-flash`。

## 评分模型也要被评测

评分模型自己也会出错。如果它会放过真实问题，后面所有的分数都没有意义。所以先建了校准集 `scenarios/v5_judge_calibration.json`：从 V1–V3 的真实测试记录里挑了 15 段已经知道答案的对话。

| 类型 | 数量 | 例子 |
|---|---|---|
| 坏例 | 7 | 编造运费险规则；被伪造通知骗出假单号；明明有订单却说没有；说了"帮您转人工"却没转 |
| 好例 | 8 | 完整的退货流程；正确拒绝拆封的贴身衣物；不被伪造通知欺骗 |

`python scripts/judge_calibration.py -j deepseek:deepseek-v4-pro -j openai:gpt-5.5` 的结果：

| 评分模型 | 第一版 | 修正后 |
|---|---|---|
| deepseek-v4-pro | 14/15，漏判 1 | **15/15** |
| gpt-5.5 | — | **15/15** |

第一版漏掉的是：客服说"我这就帮您转接人工客服"，但根本没有调用转人工工具。评分模型把**"说了"当成了"做了"**。修正方法是在对话记录里写明每一轮的程序记录（"本轮没有转接人工客服"），并在评分规则里强调"客服声称做了某个动作，以程序记录为准"。

两个不同厂商的评分模型独立得出同样的结论，说明评分标准本身比较稳定。

**注意：** 校准集只有 15 条，而且修正评分 prompt 时参考了它，存在过拟合风险。更严谨的做法是再留一组从未用来调 prompt 的对话做验证。

## 评分模型发现了什么

V3 场景在自动检查里，DeepSeek 和通义都是 14/14 全过。评分模型给出的结果是 DeepSeek 13/14、通义 9/14。人工核对后，大部分是真实问题：

- **编号对、内容错的引用。** 通义写"依据：R-07 运费险保障"，但 R-07 实际是换货规则；"R-04 退货时限"实际是运费规则。R-07 确实由资格工具返回过，所以引用核查没拦住。这正是 V2 笔记里写的盲区："编号对不代表内容对"。
- **说错政策细节。** "运费险需要退款成功后申请理赔"，与 F-03（揽收后自动理赔）矛盾。
- **没做到该做的事。** 用户要求"不用确认直接提交"时，通义没有生成申请，只是反问原因。

也有偏严的判断：DeepSeek 没提"这单有运费险"被判未通过（期望里确实写了，但影响不大）；取消后只说"已取消"、没说"未提交"。这类需要人看一眼再决定。

**由此改进了程序核查：** 引用核查新增"标题核对"，编号后写的标题和真实标题毫无关系时（如"R-07 运费险保障"），程序直接标记。阈值设得很保守，只抓明显的；"退货商品需保持完好"这种措辞改写交给评分模型判断。**规则抓明显的，模型抓微妙的**，两层各管一段。

## 可观测性

| 能力 | 在哪看 |
|---|---|
| 每次模型请求、每次工具调用的耗时和 token | 网页右侧"幕后"面板；回放记录 `raw.jsonl` |
| 本轮耗时拆分：模型推理 vs 工具执行，以及首字时间 | 网页每轮底部 |
| 网页版每轮对话的完整链路日志 | `runs/traces/日期.jsonl` |
| 每轮平均耗时、P90、首字时间、tokens、工具调用次数 | 评测报告的总览卡片 |

几个从数据里看到的事实：

- **时间几乎都花在模型上。** 工具（查 SQLite、检索知识库）通常几十毫秒；一轮 4–12 秒基本都是模型推理和生成。
- **通义比 DeepSeek 慢约 3 倍**（每轮 12.4 秒 vs 4.4 秒，首字 11.2 秒 vs 3.6 秒）。对客服场景，首字时间直接影响体验。
- **每轮约 1.2 万 tokens。** 大头是重复发送的 system prompt、工具定义和历史。这是后续做 prompt 缓存、精简工具描述的依据。

## 踩坑记录

1. **并发评测拖慢了被测模型。** 评分（6 路并发调用 DeepSeek）和回放同时进行，DeepSeek 回放的耗时从 6 秒涨到 87 秒，那一轮的耗时数据作废。评测和压测要分开跑，否则可观测数据本身就是错的。
2. **默认超时太长。** 一次网络抖动让评分请求卡住，SDK 默认超时 10 分钟加重试，整个评测卡了 40 分钟。评分客户端改为 2 分钟超时。
3. **额度用完要立刻停。** OpenAI 账户额度耗尽后，回放脚本对剩下 13 个场景逐个报错。改为遇到额度不足或认证失败时，直接停止该厂商。
4. **临时网络错误整场景重试一次**，不让一次抖动毁掉整个场景的结果。

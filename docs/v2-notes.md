# V2 学习笔记：知识库检索（RAG）

## 这一版做了什么

V0、V1 把 6 条售后政策直接写在 system prompt 里。V2 把政策扩充成 8 个文档、42 条条款，放进知识库 `knowledge/`，模型需要时调用 `search_policy` 检索，回答末尾注明依据的条款编号。

```
用户："衬衫想退，运费险能赔多少，多久到账"
  │
  ├─ list_my_orders(keyword="衬衫")      → 找到 LJ10010002
  ├─ get_order_detail(LJ10010002)        → 有运费险，签收 3 天
  ├─ search_policy("运费险理赔金额")      → F-02 理赔金额、F-03 理赔到账 …
  │
  └─ 回复："您这单有运费险……江浙沪皖 10 元，其他地区 12–25 元……72 小时内赔付到原支付账户。
           依据：F-02 运费险理赔金额；F-03 运费险理赔到账"
```

## RAG 的三步

| 步骤 | 做法 | 代码 |
|---|---|---|
| 切分 | 按"## 条款"切，一条条款一个 chunk，自带编号和标题 | `knowledge.load_chunks()` |
| 索引 | 离线算好每条的向量，存到 `data/kb_index.json` | `scripts/build_index.py` |
| 检索 | 用户提问时找出最相关的几条交给模型 | `knowledge.Retriever.search()` |

**切分为什么按条款切：** 文档是我们自己写的，结构清晰，一条规则正好一段。按固定字数切会把一条规则拦腰截断，检索到半句话。真实项目里文档往往没这么整齐，切分策略是 RAG 效果的第一个关键点。

**索引里为什么带上文档标题：** 每段参与检索的文本是"文档标题 + 条款标题 + 正文"。条款正文里经常不出现关键词，比如 F-02 正文只写"按首重标准理赔"，没有"运费险"三个字，靠标题补上。

## 三种检索方式

| 方式 | 原理 | 擅长 | 不擅长 |
|---|---|---|---|
| BM25 | 关键词重合度 | 精确词："专票""运费险" | 同义改写："快递员送来我能不要吗"→拒收 |
| 向量 | 语义相似度（embedding） | 同义、口语化表达 | 精确的专有名词、编号 |
| 混合 | 两路结果按名次融合（RRF） | 取长补短 | 多一次 embedding 调用 |

中文 BM25 通常需要分词库，这里用了更简单的办法：中文按"单字 + 相邻两字"切，两字组合能覆盖大多数中文词，不需要额外依赖。

## 检索评测

只看几个例子很难判断哪种检索更好，所以建了一个测试集 `scenarios/v2_retrieval.json`：37 个口语化问题，每题标注正确的条款。运行 `python scripts/eval_retrieval.py`，只调用 embedding 接口，成本几分钱。

| 检索方式 | Hit@1 | Recall@3 | MRR |
|---|---|---|---|
| BM25 | 68% | 88% | 0.785 |
| 向量 · 通义 text-embedding-v4 | 73% | 89% | 0.820 |
| **混合 · BM25 + 通义** | **84%** | 89% | **0.881** |
| 向量 · OpenAI text-embedding-3-small | 73% | 85% | 0.803 |
| 混合 · BM25 + OpenAI | 76% | 86% | 0.825 |

- **Hit@1**：第一条结果就是正确条款的比例
- **Recall@3**：正确条款出现在前 3 条里的比例。模型拿到的是前 4 条，这个指标更接近实际效果
- **MRR**：正确条款排名的倒数的平均值，越接近 1 越好

结论：混合检索最好；中文场景下通义的向量模型优于 OpenAI 的小模型。默认配置是混合 + 通义。

**改内容比改算法有效。** 第一次评测时，"退货险能赔多少"用任何方法都找不到 F-02，因为知识库里只写了"运费险"，而用户口语里常说"退货险"。在文档标题里加上别名后重建索引，混合检索的 Hit@1 从 78% 提升到 84%。

## 引用核查

prompt 要求模型在回复末尾写"依据：F-02 运费险理赔金额"。但测试发现，**出处本身也会被编造**。qwen-plus 有时根本不检索，却写出了看起来很正规的依据：

- "依据：F-05 生鲜类商品售后时效"：知识库里没有 F-05
- "依据：F-03 增值税专用发票开具条件"：F-03 实际是运费险条款
- "依据：F-02 运费险理赔金额"：编号和标题都对，但内容是编的（"首重 12 元，每公斤加 3 元"）

所以加了一道程序检查（`Session._check_citations`）：回复里出现的条款编号，必须在本会话里被 `search_policy` 真正返回过，否则标记为"编造引用"。网页上会显示红色警告，批量测试会把它算作失败。

这道检查只能证明"引用的条款确实检索过"，不能证明"回答内容和条款一致"（第三个例子就骗过了编号检查，只是这次它恰好也没检索）。内容是否忠实于条款，需要 V5 用模型评分来判断。

## 其他设计决策

| 决策 | 原因 |
|---|---|
| 检索做成工具，由模型决定何时调用 | 闲聊、纯查订单时不检索，省 token。代价是模型可能该查不查，需要靠测试发现 |
| 工具描述里列出知识库覆盖范围 | 一开始只写了"退换货、运费"等，问"人工客服几点下班"时 DeepSeek 和 OpenAI 都不检索，直接答错。列出覆盖范围后两家都能正确检索 |
| 向量接口出错时退回 BM25 | 检索降级总比客服整个不可用好 |
| 知识库没有的内容，明确说"没有查到" | 测试了"花呗分期""以旧换新"两个知识库里没有的问题，检验模型会不会自己编 |
| 修改文档后必须重建索引 | 用内容指纹检测，文档改了而索引没更新时直接报错，避免检索结果和文档对不上 |

## 踩坑记录

1. **订单列表没给签收日期，模型就自己编。** 列表里只有"已签收 3 天"，通义回答时说"10 月 5 日签收"（实际是 10 月 8 日）。给工具加上 `signed_at` 字段。模型需要的信息，工具就该直接给。
2. **模型版本差异巨大。** `qwen-plus` 是旧别名，V2 场景里 14 个只通过 4 个，几乎不调用检索。换成同一档次的新模型 `qwen3.7-plus` 后通过 12 个，零编造引用。选型时别只看厂商名，要看具体模型版本。
3. **推理模型偶尔返回空回复。** qwen3.7-plus 有一次既没有文字也没有工具调用。agent loop 加了兜底：整轮没有任何输出时自动重试一次。

# V1 学习笔记：工具调用与 agent loop

## 这一版做了什么

V0 的客服只能"说"：看不到订单，只能让用户自己报签收时间、自己去 App 查物流。V1 接入了模拟商城数据库和 5 个工具，客服可以自己查了。

| 工具 | 作用 |
|---|---|
| `list_my_orders` | 按状态、商品关键词列出当前用户的订单 |
| `get_order_detail` | 订单详情：商品标签（贴身 / 生鲜 / 数码）、运费险、各环节时间、已签收天数 |
| `get_logistics` | 物流轨迹，以及距最近一次更新过了多少小时 |
| `get_aftersale_status` | 售后进度，以及仓库签收后过了几个工作日 |
| `transfer_to_human` | 转人工，取代 V0 的 `[转人工]` 文本标记 |

## agent loop 是怎么转起来的

```
用户："空气炸锅怎么还没到"
  │
  ├─ 第 1 步：请求模型（带上 5 个工具的定义）
  │    模型输出：调用 list_my_orders(keyword="空气炸锅")
  │    程序执行 → 找到 LJ10010004 → 结果追加进历史
  │
  ├─ 第 2 步：再请求模型（历史里多了上一步的调用和结果）
  │    模型输出：调用 get_logistics(order_id="LJ10010004")
  │    程序执行 → 最后更新 108 小时前 → 结果追加进历史
  │
  └─ 第 3 步：再请求模型
       模型输出：纯文字回复，没有工具调用 → 本轮结束
```

核心代码在 [session.py](../agent/session.py) 的 `send()`，不到 50 行。要点：

1. **模型从不直接执行任何东西。** 它只输出"我想调用哪个工具、参数是什么"，执行的永远是程序。
2. **一轮用户对话 = 多次模型请求。** 上面的例子请求了 3 次模型，所以 token 消耗比 V0 高很多。
3. **要有上限。** `MAX_STEPS = 6`，最后一步禁止调用工具，防止模型陷入反复调用。
4. **失败要回滚。** 中途请求失败时，把本轮追加的消息全部撤回，否则历史里会留下"有调用、没结果"的残缺记录，下次请求直接报错。

## 关键设计决策

| 决策 | 原因 |
|---|---|
| `user_id` 由程序注入，不是工具参数 | 模型无法查询别人的数据，无论用户怎么说。这是在架构上防越权，而不是靠 prompt 让模型"别查" |
| 别人的订单和不存在的订单返回同样的结果 | 不泄露"这个订单号存在、只是不属于你" |
| 日期计算放在工具里 | 工具直接返回"已签收 12 天""已过 0 个工作日"。大模型做日期加减很容易出错 |
| 工具只返回事实，不下结论 | "能不能退"仍由模型依据政策判断。V3 会加资格校验工具，届时对比两种做法 |
| 工具错误作为结果返回给模型 | 订单不存在、参数不对，都变成一条 `is_error` 的结果，让模型自己纠正或告诉用户，而不是程序崩溃 |
| 参数一律校验 | 模型生成的参数是不可信输入：可能缺字段、类型错、枚举值越界 |
| 关键词宽松匹配 | 见下方"踩坑记录" |

## 各厂商 tool calling 的格式差异

用 `/debug` 可以看到完整请求。差异汇总：

| | Anthropic | OpenAI 兼容 |
|---|---|---|
| 工具定义 | `{name, description, input_schema}` | `{type: "function", function: {name, description, parameters}}` |
| 模型发起调用 | `content` 里的 `tool_use` 块 | `message.tool_calls` 数组 |
| 参数格式 | 已解析的对象 | JSON 字符串，需要自己 `json.loads` |
| 流式时的调用 | SDK 自动拼好 | 按 `index` 分片到达，要自己拼接 |
| 回传结果 | 一条 `user` 消息，内含多个 `tool_result` 块 | 每个调用一条 `role: "tool"` 消息 |
| 思考过程 | thinking 块原样回传 | DeepSeek 等厂商要求工具调用的那一步回传 `reasoning_content` |

适配层在 [providers/](../agent/providers/)，agent loop 本身完全不关心是哪家模型。

## 踩坑记录

1. **gpt-5.5 在 Chat Completions 接口下不能同时用工具和推理。** 带工具时 `reasoning_effort` 只能设为 `none`，否则 400。要推理需改用 OpenAI 的 Responses API。所以 V1 里 OpenAI 是在"不思考"模式下跑的，和 V0 的配置不同。
2. **随机生成的填充数据干扰了测试。** 一开始填充订单里也有保温杯、围巾，模型按商品名查到好几单，只能反问用户"是哪一单"。测试失败的原因是数据，不是模型。修复：填充订单不使用场景里出现过的商品。
3. **工具太"严格"，导致模型答错。** 用户说"降噪耳机"，商品名是"降噪蓝牙耳机 Pro"，SQL `LIKE` 查不到，OpenAI 和通义都告诉用户"您没有这个订单"。这是工具设计的问题，不是模型的问题。修复：按字符顺序宽松匹配；查不到时在结果里提示模型换个短关键词再试。
4. **prompt 规则互相矛盾。** "满足条件就转人工"和"询问用户时不要调用"两条规则，模型理解为"要先问用户同意再转"。修复：明确"出现上述情况直接调用，不需要征求同意"。

# V4 学习笔记：MCP 化

## 这一版做了什么

V1–V3 里，客服 Agent 直接 `import` 商城的代码、直接读写数据库。真实世界里这两边通常属于不同团队：客服平台是一个系统，商城的订单、售后是另一个系统。

V4 把它们拆开，中间用 **MCP（Model Context Protocol）** 连接：

```
┌──────── 客服 Agent（agent/）────────┐              ┌──────── 商城 MCP 服务（mall/）────────┐
│ agent loop、模型适配                │              │ 订单 / 物流 / 售后 / 知识库工具        │
│ 转人工规则、引用核查、单号核查       │   MCP 协议    │ 资格规则引擎                          │
│ 确认卡片（计算确认签名）             │ ◄──────────► │ 数据库、待确认申请、审计日志           │
│ 自己的工具：转人工                   │  HTTP + 令牌  │ 身份令牌验签、确认签名验签              │
│ 不 import 任何商城代码               │              │ 不 import 任何客服代码                 │
└─────────────────────────────────────┘              └───────────────────────────────────────┘
```

`agent/` 目录里已经没有任何一行代码引用 `mall/`。客服 Agent 启动时连接商城服务，**自动发现**它提供了哪些工具，再交给大模型。

## MCP 解决什么问题

没有 MCP 时，每个想用商城能力的 Agent 都要单独对接一遍：各写各的调用代码、各自维护工具描述。MCP 是一个开放协议，业务方按协议提供一次服务，任何支持 MCP 的客户端都能接入：

| 接入方 | 方式 | 验证 |
|---|---|---|
| 我们的客服 Agent | HTTP（Streamable HTTP） | 全部场景回归测试 |
| Claude Desktop 等 MCP 客户端 | stdio（客户端把服务作为子进程启动） | 用 SDK 的 stdio 客户端模拟验证 |

商城服务提供三类东西：

| 类型 | 内容 |
|---|---|
| 工具（给大模型） | search_policy、list_my_orders、get_order_detail、get_logistics、get_aftersale_status、check_return_eligibility、create_aftersale_request |
| 工具（只给宿主程序） | get_my_profile、confirm_aftersale_request、cancel_aftersale_request，带 `meta.host_only` 标记 |
| 资源 | `kb://clauses`：知识库全部条款，客服 Agent 用它核对引用标题 |

## 设计难点一：身份怎么跨服务传递

V1 起的原则是"user_id 由程序注入，模型无法指定"。拆成两个服务后，商城怎么知道是谁在查？

| 方案 | 问题 |
|---|---|
| 工具参数里带 user_id | 参数是大模型生成的，用户一句"帮我查 u1002 的订单"就可能被篡改 |
| 请求头里直接写 user_id | 请求头同样可以伪造。MCP SDK 的文档也特意提醒：请求头是客户端输入，不能当作身份证明 |
| **请求头里带签名令牌** ✅ | 用户登录商城时拿到令牌（模拟登录服务签发），客服 Agent 只负责转交。商城用密钥验签后解出 user_id。没有密钥就造不出有效令牌 |

测试：篡改令牌最后几个字符，商城返回"身份令牌签名无效"。

## 设计难点二："必须用户确认"怎么跨服务保证

V3 里，执行写操作的函数在客服 Agent 进程里，大模型调用不到就够了。拆开后执行逻辑在商城，需要商城自己能确认"这真的是用户点的"。设了三道防线：

1. **大模型看不到确认工具。** `confirm_aftersale_request` 带 `host_only` 标记，客服 Agent 不会把它交给大模型。测试：脚本模拟模型强行调用，得到"不存在名为 confirm_aftersale_request 的工具"。
2. **确认必须带签名。** 用户点击按钮后，客服 Agent 的界面层用共享密钥计算签名一起发送；商城验签。大模型拿不到密钥。测试：错误签名被拒绝，"这个操作没有经过用户在界面上确认"。
3. **待确认申请归商城保存。** V3 存在客服 Agent 内存里，V4 改为商城的 `pending_actions` 表，绑定用户、15 分钟过期。测试：别人的令牌加正确格式的签名，商城回复"没有找到这张待确认的申请"。

写操作的规则（哪些申请在等确认、谁能确认、怎么执行）归业务方所有，客服 Agent 只负责转交用户的确认动作。这和"安全靠架构"的思路一致：哪怕客服 Agent 有漏洞，商城也不会执行没经过用户确认的操作。

## 回归测试：怎么证明拆分没有改坏

重构架构最怕"看起来能跑，其实某个角落坏了"。V0–V3 积累的场景正好派上用场：拆分后用 DeepSeek 把所有场景重跑一遍，再用 V5 的评分模型打分，和拆分前对比。

| 场景集 | 拆分前 | 拆分后 |
|---|---|---|
| V1（16 个） | 15/16 | 15/16 |
| V2（14 个） | 14/14 | 14/14 |
| V3 自动检查（14 个） | 14/14 | 14/14 |
| V3 评分模型 | 13/14 | 14/14 |
| 每轮耗时 / 首字 | 4.4s / 3.6s | 4.8s / 3.9s |

功能没有退化。V1 唯一的失败和拆分前相同（资格工具让模型跳过了订单详情查询，答案正确）。评分从 13 到 14 主要是模型自身的波动，不代表架构让回答变好了。耗时增加约 0.3 秒，与单次 MCP 工具调用 8–9 毫秒、每轮约 2–3 次工具调用的量级相符。

数据：`runs/20261012-170730/`（V1）、`runs/20261012-170913/`（V2）、`runs/20261012-171052/`（V3 + 评测报告）。

## 其他细节

- **参数 schema 适配。** MCP SDK 根据函数签名生成的 schema 里，可选参数写成 `anyOf: [string, null]`，还带 `title`、`default`。部分模型对这种写法理解不稳定，客户端在交给大模型前整理成更简洁的形式（`simplify_schema`）。
- **工具描述保持不变。** 迁移时从 git 历史里取回原来的工具描述，原样放到 MCP 服务上。这样回归测试的对比只反映架构变化，不混入 prompt 变化。
- **故障隔离。** 商城服务连不上时，工具调用返回"商城服务暂时不可用，请稍后再试或转人工"，对话不会崩溃。
- **本地开发自动启动。** 客服 Agent 发现本机商城服务没运行，会自动在后台启动一个，退出时一并关闭。
- **性能。** 每次工具调用新建一个 MCP 连接，实现最简单。本机测得单次工具调用 8–9 毫秒，相比模型推理的秒级耗时可以忽略。

## 接入 Claude Desktop

在 Claude Desktop 的配置文件 `claude_desktop_config.json` 里加入（路径换成你的项目路径）：

```json
{
  "mcpServers": {
    "linjian-mall": {
      "command": "/你的路径/aftersales-agent/.venv/bin/python",
      "args": ["-m", "mall.mcp_server", "--stdio"],
      "env": {"PYTHONPATH": "/你的路径/aftersales-agent", "MALL_STDIO_USER": "u1001"}
    }
  }
}
```

重启 Claude Desktop 后，就可以直接问"我的空气炸锅到哪了"。stdio 方式没有请求头，用 `MALL_STDIO_USER` 指定本地演示用户，只适合本机演示。确认类工具虽然也会出现，但没有签名密钥调用不成功，写操作仍然安全。

## 踩坑记录

1. **SDK 大版本变化。** 安装到的是 MCP Python SDK 2.3，`FastMCP` 已更名为 `MCPServer`，客户端也换成了统一的 `Client`。没有凭记忆写代码，而是先读已安装 SDK 的源码，再写一个最小原型验证"请求头传递 → 工具读取 → 结果返回"整条链路，然后才开始重构。
2. **进程清理命令写得太宽。** 测完原型后用 `pkill -f "server.py" -n` 清理，误杀了另一个同名进程。之后启动后台服务时都记录进程号，只按进程号停止。

## 发现

1. **数据权限全员通过。** 查别人的订单、自称管理员、订单号不存在，三家都处理正确。这不是因为模型"自觉"，而是 `user_id` 由程序注入，模型根本没有查别人数据的途径。安全靠架构，不靠 prompt。

2. **工具化让错误变得可检测。** 通义在 handoff-02 说"我这就帮您转接"却没调用工具，和 V0 第二轮 DeepSeek 犯的是同一个错误。区别在于：V0 时只能靠人工读回复发现；现在程序明确知道"没有调用 transfer_to_human"，自动检查直接报错，线上也可以据此兜底。

3. **通义的问题从"编造政策"变成了"不用工具、编造数据"。** 它经常不查就答，或者只查了列表就说出列表里没有的信息（签收日期、是否有运费险）。数据类幻觉比政策类幻觉更危险，因为用户更难识别。

4. **OpenAI 关闭推理后偏保守。** 两轮都在"要求赔偿"场景里只提议转人工、等用户确认。这和 prompt 的意图不符，但说明它对"未经同意不执行动作"很谨慎，到 V3 做写操作时反而是优点。

5. **DeepSeek 在 V0、V1 都是最稳的**，并且最快。它的工具调用最多（27 次），比如 refund-01 会额外查订单详情，用多花的 token 换更完整的信息。

## 遗留问题

- OpenAI 的 handoff-02 和通义的工具使用问题，可以继续调 prompt，但收益有限，更适合靠模型选型解决。
- 自动检查覆盖不到回答内容的正确性（order-01 就是例子），人工复核 48 段对话很费时间，V5 需要引入 LLM 评分。
- OpenAI 带工具时无法开启推理，如果要公平比较，需要为 OpenAI 实现 Responses API 适配。
